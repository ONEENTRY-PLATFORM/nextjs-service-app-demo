### 2.12. [СЕРЬЁЗНО] ✅ `components/layout/booking-page/useBookingSubmit.ts:37`

*Измерение: `rule:attribute-values`*

**Суть:** Интервал записи (type: 'timeInterval') строится в локальном времени клиента, а профиль форматирует его по UTC — забронированное время отображается со сдвигом на таймзону (в Дубае −4 часа)

**Рекомендация:** Строить интервал в UTC: new Date(Date.UTC(y, m, d, hh, mm)) (и конец аналогично), тогда «10:00» уйдёт как 10:00Z и getUTCHours() в OrderDateTime вернёт то, что выбрал пользователь.

> Проверка: Находка подтверждается по всем пунктам. (1) Правило attribute-values действительно требует UTC-семантику по всей цепочке timeInterval: фильтрация слотов по UTC, «Time formatting — from UTC hours!» (getUTCHours/getUTCMinutes) и отправка выбранного слота как value: [[startISO, endISO]] — цитата ruleQuote дословная. (2) Код по file:line точен: useBookingSubmit.ts:37 — `const start = new Date(y, m, d, hh, mm)` строит Date в локальной таймзоне браузера ('use client'-хук), конец интервала — от start.getTime(). Слоты берутся не из CMS-UTC-интервалов, а из хардкода TIMES ('09:00'…'20:00', constants.ts) — «настенное» время салона. При сериализации в createOrder Date уходит как UTC-ISO со сдвигом на офсет клиента: «10:00» в Дубае (UTC+4) → 06:00Z. (3) Чтение подтверждено: OrderDateTime.tsx стр. 26–30 форматирует именно через getUTCMonth/getUTCDate/getUTCHours/getUTCMinutes — пользователь увидит 06:00 и, при переходе через полночь UTC, смещённую дату. Оговорка, не меняющая вердикт: по контент-плану у формы `order` поля пока не заведены (attributes = {}), так что до заведения поля `interval` баг может не проявляться визуально, но код-нарушение правила реально и проявится для всех клиентов вне UTC (вся целевая аудитория — Дубай). Severity major адекватна: запись создаётся, но время в профиле и в CMS сдвинуто на −4 часа.

> Общая оценка критика: Разбиение 22 правила + 20 скиллов + 5 сквозных проверок хорошо покрывает «внутренность» интеграции с OneEntry (данные, атрибуты, формы, заказы, auth, перфоманс, локализация), но систематически упускает «обвязку» Next.js вокруг CMS и прод-поверхности. Подтверждённые кодом дыры покрытия группируются в шесть кластеров: (1) SEO из CMS — sitemap/robots с неверным базовым URL из NEXT_PUBLIC_ONEENTRY_URL, generateMetadata на 16 страницах, отсутствие metadataBase, JSON-LD; (2) поверхности ошибок — нет ни одного error.tsx/global-error.tsx; (3) безопасность — dangerouslySetInnerHTML для CMS-HTML в 6 файлах, публичные диагностические роуты test-connection/api-test, отсутствие CSP, объём прав NEXT_PUBLIC-токена в клиентском бандле; (4) конфигурация next.config.ts (битый fonts-rewrite, staleTimes, remotePatterns); (5) верификация — jest-тесты интеграции не оцениваются (есть только правило playwright-e2e), а аудит не сверяется с живым состоянием админки (payment_success/payment_canceled отсутствуют в CMS при живом роутинге — сломан пост-оплатный флоу); (6) a11y CMS-контента отсутствует как измерение вовсе. Оценка полноты: ~75% — статический код против правил SDK проверен плотно и с малым риском пропусков, но рантайм-/прод-аспекты и консистентность код↔живая CMS остались слепой зоной; рекомендую добавить 4–6 агентов по кластерам выше, в первую очередь SEO-роуты, error-границы и безопасность CMS-HTML/токена.

## C.6. Events — события CMS (ЗАКРЫТО 2026-07-16)

**Статус: ✅ ЗАВЕДЕНО И ПРОВЕРЕНО.** Пользователь создал 6 событий; сброс пароля проверен живым прогоном (`generate-code` → **201**).

| Идентификатор | Название | Назначение | Используется |
|---|---|---|---|
| `reset_password` | Reset password | Сброс пароля: выдаёт OTP и авторизует смену | `ForgotPasswordForm` (`generateCode`), `VerificationForm` (`checkCode`, resend), `ResetPasswordForm` (`changePassword`) — **одно событие на весь флоу** |
| `otp` | Registration otp | OTP активации аккаунта | `VerificationForm` resend при `action === 'activateUser'` — **сейчас дремлет**: активация выключена (`isCheckCode: false`) |
| `generate_otp` | Generate code | `formType: 'send_code'` | кодом **не используется** |
| `order`, `order_change`, `order_canceled` | — | уведомления по статусам заказа (`upcoming`/`completed`/`canceled`, storage id 1) | сервером, не фронтом |

**Важно:** фактические идентификаторы отличаются от типовых в правиле `auth-provider` (`reset_password`, а не `password_reset`; `otp`, а не `user_registration`) — константы в `components/forms/authEventMarkers.ts` приведены к фактическим.

**Почему маркеры нельзя подтвердить «пробником»** (стоило времени, не повторять):

- `Events.getAllEvents()` → **401** с токеном проекта, хотя правило `auth-provider` и скилл `create-subscription-events` называют метод публичным с SDK 1.0.150 (стоит 1.0.155). Скрипт: `.claude/temp/inspect-events-public.mjs`.
- `generateCode` отвечает `400 "User already has a code"`, пока у пользователя есть невыданный код — **несуществующее событие даёт ТУ ЖЕ ошибку**. Пробники порядко-зависимы: первый вызов выигрывает и маскирует все следующие.
- Код живёт **дольше** `systemCodeTlsSec` (120 с — кулдаун ресенда, не TTL кода; фактически истёк за ~14 мин).
- `checkCode` возвращает `false` на любой маркер, включая несуществующий, — неотличимо от неверного кода.
- Достоверно: список через внутренний admin API (`node .claude/temp/list-events.mjs`) + живой прогон флоу.
